## 一、后端修改（共 2 处）

### 修改 1：crud/favorite.py 拼写错误 `lable` → `label`

#### 修改文件
`新闻软件（无前端）/crud/favorite.py`

#### 修改原因
原代码第 58 行存在拼写错误：`Favorite.created_at.lable('favorite_time')`。
SQLAlchemy 的列对象没有 `lable` 方法（正确拼写为 `label`），
导致 **GET /api/favorite/list（收藏列表接口）一调用就直接 500 报错**。
该接口是个人中心"收藏列表"功能的必经接口，前端无法绕过，
且"收藏列表"是需求明确要求的功能，因此必须修复。

#### 修改内容
```python
# 修改前
order = (select(News,Favorite.created_at.lable('favorite_time'),Favorite.id.label('favorite_id'))
# 修改后
order = (select(News,Favorite.created_at.label('favorite_time'),Favorite.id.label('favorite_id'))
```
（仅把 `lable` 改为 `label`，其余代码未动）

#### 修改后效果
收藏列表接口的查询语句可以正常构建，不再因 AttributeError 直接 500。

### 修改 2：routers/favorite.py 字段名拼写错误 `favorite_if` → `favorite_id`

#### 修改文件
`新闻软件（无前端）/routers/favorite.py`

#### 修改原因
原代码第 65 行把收藏记录的 id 存成了错误字段名 `'favorite_if'`（应为 `'favorite_id'`）。
收藏列表接口用 Pydantic 模型 `FavoriteNewsItemResponse` 校验数据时，
该模型要求 `favoriteId` 字段（对应 `favorite_id`），因字段名错误导致校验失败：
**只要收藏列表里有 1 条及以上数据，接口就返回 500**（列表为空时没有数据要校验，所以不报错，这也是空列表能正常返回的原因）。
该接口是个人中心"收藏列表"功能的必经接口，前端无法绕过，因此必须修复。

#### 修改内容
```python
# 修改前
'favorite_time':favorite_time,
'favorite_if':favorite_id
# 修改后
'favorite_time':favorite_time,
'favorite_id':favorite_id
```
（仅把字典 key `favorite_if` 改为 `favorite_id`，其余代码未动）

#### 修改后效果
收藏列表接口在**有收藏数据时也能正常返回**，个人中心"收藏列表"页面可以正常展示、分页、取消收藏、清空。
（已实测：添加 1 条收藏后调用接口，返回 200 + 收藏列表数据。）

## 四、前端对后端特殊情况的兼容（后端零修改）

以下后端存在的"特殊情况"没有修改后端，而是由前端适配：

### 1. Token 认证格式（关键！）
`新闻软件（无前端）/utils/auth.py` 中提取 token 的代码为
`authorization.replace("Beared","")`——"Beared" 是 "Bearer" 的拼写错误，
导致标准的 `Authorization: Bearer xxx` 头无法正确解析。
**前端方案**：`js/api.js` 中所有请求直接发送 `Authorization: <原始token>`（不带任何前缀），
后端原样匹配 token 成功。前端无需也不能发送 "Bearer " 前缀。

### 2. 历史记录删除接口按 newsId 删除
`routers/history.py` 的路由参数名为 `history_id`，但 `crud/history.py` 实际按
`History.news_id == 传入值` 删除记录。
**前端方案**：`js/api.js` 的 `deleteHistory(newsId)` 传入**新闻 id**，即可正确删除该新闻对应的浏览记录。

### 3. 接口字段命名不一致
- 新闻列表 `/api/news/list`、分类 `/api/news/categories`：返回 **snake_case**
  （`publish_time`、`category_id`、`sort_order`）
- 新闻详情 `/api/news/detail`：返回 **camelCase**（`publishTime`、`categoryId`、`relatedNews`）
- 收藏/历史列表：经 Pydantic 序列化后返回 camelCase（`publishedTime`、`favoriteTime`、`viewTime`）
**前端方案**：`js/api.js` 中的 `normalizeNewsItem()` 统一归一化成一套字段，各页面无需关心来源差异。

### 4. 需要登录的接口未登录时的表现
收藏、历史、用户等接口依赖 token，未登录调用会返回 401。
**前端方案**：仅当"带着 token 访问受保护接口"返回 401 时，才清除登录态、提示重新登录并跳转个人中心；
**登录/注册接口返回 401（如"用户名或密码错误"）则直接展示后端提示**，避免被误判为"登录过期"。

### 5. 后端自定义异常响应格式（重要）
后端在 `utils/exception.py` 注册了全局异常处理器，**所有错误响应的 JSON 格式都不是标准的
`{"detail": "..."}`，而是 `{"code": 状态码, "message": 提示语, "data": ...}`**。
例如：重复注册返回 `{"code":400,"message":"用户已存在"}`，登录失败返回 `{"code":401,"message":"用户名或密码错误"}`。
**前端方案**：`js/api.js` 的错误解析**优先取 `message` 字段，其次才取 `detail`**，
从而正确显示"用户已存在 / 用户名或密码错误"等真实原因，而不是笼统的"请求失败（HTTP xxx）"。

### 6. 登录/注册表单的静默拦截与错误可见性
- 表单加 `novalidate`：避免浏览器原生 `required` 校验静默拦截 submit 事件（拦截时只弹不易察觉的原生气泡，看起来像"点击没反应"），改由前端 JS 校验并用 toast 明确提示（"两次输入的密码不一致"等）。
- 提交按钮点击后显示"登录中…/注册中…"状态，任何异常都会以 toast 展示具体原因，杜绝"点了没反应"。

### ai_server.py v2 加固说明（解决"一直在思考"）
旧版每个提问都会先连接 Milvus，Milvus 未启动时 `MilvusClient` 构造函数会**长时间挂起**
（实测 90 秒+无响应），前端因此一直显示"正在思考…"。v2 改进：
1. **问候语直接回复**（你好/您好/hi 等），不依赖 Milvus、不调用大模型，秒回；
2. 提问前先用 **TCP 快速探测 Milvus 可达性**（2 秒超时），不可达立即返回
   "知识库服务（Milvus）未启动"提示；
3. 知识库构建、检索、大模型调用全部放入**线程池执行并带超时保护**
   （构建 120s / 问答 90s），超时返回明确错误，服务始终保持响应；
4. 启动时若 Milvus 可达则自动构建知识库（`lifespan`），首次提问无需等待建库。
前端 `API.chat()` 同步增加 AbortController 超时（130 秒），杜绝无限等待。

## 六、Milvus 环境说明（由用户自行部署 Milvus 服务）

### 背景
本机最初未安装 Milvus。曾尝试用 **Milvus Lite**（嵌入式）方案配置（创建 `D:\Milvus`、安装 milvus-lite 包、
把连接改成本地文件模式），**该方案已按用户要求全部撤回**：
- `D:\Milvus` 文件夹已删除；
- `milvus-lite` / `faiss-cpu` / `pyarrow` 包已卸载；
- 代码连接方式已还原为**标准 Milvus 服务模式**（`MILVUS_URI = http://localhost:19530`）。

Milvus 服务由**用户自行部署**（Docker 部署 Milvus Standalone 等），启动后 `ai_server.py` / `main.ipynb`
即可直接连接使用（默认地址 `http://localhost:19530`、数据库 `AI_rag`、集合 `Knowledge_chunks`）。

### 保留的跨模式修复（与 Milvus 部署方式无关，建议保留）
在 Milvus Lite 调试过程中发现并修复了 3 个**与部署方式无关**的真问题，已保留在代码中：

| 修复 | 文件 | 说明 |
|---|---|---|
| `system_prompt` 由元组改为单个多行字符串 | `ai_server.py`、`main.ipynb` | 元组会被序列化成字符串数组，DeepSeek API 报 400（"invalid type: string, expected ... ChatCompletionRequestContentBlock"）；实测改为单字符串后正常 |
| 检索前调用 `load_collection()` | `ai_server.py`、`main.ipynb` | Milvus 集合处于 released 状态时 search 报错（code=101，需先 load）；Milvus Lite 重启后必现，完整 Milvus 服务同样需要 |
| 切分前剔除纯 `=====` 分隔行 | `ai_server.py`、`main.ipynb` | 分隔行被切成独立 chunk 会污染向量检索（top-5 全是分隔线/无关内容）；剔除后 chunk 数 44→14，检索命中率大幅提升（"如何收藏新闻？"命中 0.78） |

### 修改后效果
- 部署好 Milvus 服务并启动后，`ai_server.py` 会自动建库（`AI_rag`/`Knowledge_chunks`）、导入知识库并正常问答；
- 问候语秒回；未启动 Milvus 时快速返回提示，不会卡住（v2 加固，见上文）。
